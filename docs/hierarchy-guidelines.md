# 階層構造の設計ガイド

## 設計原則

この仕様では、フローを「詳しい／簡単」という曖昧な粒度で分けません。誰から観測できる振る舞いか、どの責務を説明するかで層を分けます。

~~~text
Experience Flow
  ユーザーが操作・観測できること
          │ expands
          ▼
Realization Subflow
  Interaction: 画面内の入力・検証・状態
  Orchestration: システム間の要求・判断・保存
~~~

Experienceノードは外側に対する振る舞いの契約です。Subflowは、その契約を実現する検証可能な手順です。

## Experience Flowの基準

トップレベルには、ユーザーが知覚できる次の内容だけを置きます。

- 画面や案内を見る
- 情報を入力する
- 操作を実行する
- 成功、失敗、待機などの結果を認識する
- ユーザーから見た目的が次の段階へ変わる

よい例:

- 認証情報を入力する
- ログインを試行する
- トップ画面へ移動する
- 認証エラーを確認する

Experience Flowに置かないもの:

- APIを呼ぶ
- 外部認証へ問い合わせる
- アカウントの有効性を判定する
- セッションテーブルへ保存する
- 内部イベントを発行する

これらはユーザーが直接観測する振る舞いではないため、Orchestration Subflowへ置きます。

Experienceでは <code>view</code>、<code>action</code>、<code>event</code>、<code>state</code> だけを使用します。システム内部を示す <code>command</code>、<code>integration</code>、<code>decision</code> は使用できません。

## Subflowを作る判断

次の順序で配置先を決めます。

1. ユーザーが操作または結果を知覚できるか
   - はい: Experience Flow

2. 画面内の入力、形式検証、ボタン状態、入力エラーか
   - はい: Interaction Subflow

3. 自システム、外部システム、リソース間の要求、判断、保存か
   - はい: Orchestration Subflow

4. 振る舞いやテスト結果を変えない内部実装か
   - はい: ノードにせずTechnical mappingまたは関連リンク

### Interaction Subflow

Interactionは、1つのユーザー操作を成立させる画面内の振る舞いです。

分解する候補:

- 独立した入力項目が複数ある
- 入力形式の検証がある
- ボタン活性化やローディング状態が変わる
- 入力エラーから再入力へ戻る
- キーボード操作など別の操作経路がある

### Orchestration Subflow

Orchestrationは、1つのユーザー操作や結果を実現するシステム協調です。

分解する候補:

- ブラウザから自システムへ要求する
- 外部システムへ照会する
- 業務ルールで成功と失敗を判断する
- 状態を保存または参照する
- 複数処理を並列実行する
- イベントや応答を確定する

## ログインの境界例

Experience Flow:

~~~text
ログイン画面を見る
  → 認証情報を入力する
  → ログインを試行する
      ├→ トップ画面へ移動する
      └→ 認証エラーを確認する
~~~

「認証情報を入力する」はInteractionへ展開します。

~~~text
会員ID入力 ─→ ID形式検証 ─┐
                            ├→ ログイン操作を有効化
パスワード入力 → PW形式検証 ┘
~~~

「ログインを試行する」はOrchestrationへ展開します。

~~~text
ログイン実行
  → ログイン要求
  → 外部認証へ照会
  → 有効性判断
      ├→ プロフィール取得・監査記録・セッション作成
      └→ ログイン拒否
~~~

ボタンクリックはユーザー操作ですが、ログイン試行の開始点としてOrchestration内に置きます。トップレベルでは「ログインを試行する」という契約だけを見せます。

## 順不同と並列の違い

順序関係がないことと、同時実行することは区別します。

| mode | 意味 | 例 |
|---|---|---|
| <code>unordered</code> | どの順番でもよい | ID入力とパスワード入力 |
| <code>parallel</code> | 同時に進行できる | プロフィール取得と監査記録 |

ID入力とパスワード入力は同時に行う必要はないため、parallelではなくunorderedです。

複数の処理がすべて完了してから次へ進む場合は、後続ノードへ <code>join: all</code> を指定します。

グループは「見た目を横に揃える」ためではなく、順序や実行条件の意味を伝えるために使います。

## EntryとExitの契約

Subflowは親ノードの契約を満たすため、開始点と終了点を明示します。

- entry: Subflowへ入ったときに開始可能なノード
- exits.happy: 親の正常系結果を満たすノード
- exits.exception: 親の異常系結果を外側へ返すノード

レビューでは、次を確認します。

- entryから正常系exitへ到達できる
- 異常系が行き止まりになっていない
- 再入力ループはentryまたは修正可能な操作へ戻る
- exitの結果と、親から外へ出るエッジの意味が一致する

## 粒度を揃える基準

同じSubflow内では、隣接ノードの粒度を揃えます。

- 操作、判断、状態、イベントを区別する
- 1ノードのGiven / When / Thenを1つの結果に収める
- ノード名は実装手段より振る舞いを優先する
- API名や関数名はtechnicalへ記載する
- 別のユーザーストーリーから単独参照したい処理は、親の境界を見直す

1ノードの説明に「〜して、〜して、〜する」が複数回現れる場合は分解候補です。ただし、振る舞いを変えない関数呼び出しやログ出力までノードにしません。

## 自動配置の考え方

位置は仕様ではありません。意味上の依存関係だけをエッジとして定義し、ビューがSTAGEを算出します。

- エッジがない開始ノードは同じSTAGEに配置する
- ID入力とパスワード入力のような順不同操作は同じSTAGEになる
- 後続ノードは依存元より後ろへ配置する
- AND結合はすべての依存元より後ろへ配置する
- 再入力や再試行のloop edgeは配置計算から除外する
- 同じSTAGEの表示順はYAMLの記述順で安定させる

YAMLへcolumnや座標を記述しません。レイアウト調整のためだけに意味のないエッジを追加することも禁止します。

## L1〜L3を使用しない理由

同じノードのタイトルだけをユーザー語彙、振る舞い語彙、技術語彙へ切り替えると、構造の深さと表現の違いが混同されます。

v3ではタイトルを1つにし、役割を分離します。

- title: レビュー時に読む振る舞い
- technical: API、イベント、関数、データ構造との対応
- detail: Given / When / Then、前提、関連仕様

システム内部を詳しく読みたい場合はタイトル切り替えではなく、Orchestration Subflowを開きます。

## 作成手順

1. ユーザーが目的を達成するまでをExperience Flowだけで作る
2. 各ノードがユーザーから観測可能か確認する
3. 画面内の詳細が必要なノードへInteractionを作る
4. システム協調が必要なノードへOrchestrationを作る
5. entryと正常系・異常系exitを定義する
6. 順不同または並列の意味がある箇所だけgroupを定義する
7. エッジだけで意図したSTAGEになることを確認する
8. Experienceへ戻し、内部を閉じてもユーザーの物語が読めることを確認する

## レビューチェックリスト

- Experienceにシステム内部ノードが混ざっていないか
- 親ノードはユーザーが理解できる1つの契約か
- InteractionとOrchestrationを混在させていないか
- unorderedとparallelを区別しているか
- join条件が明確か
- entryとexitが親の前後関係と一致しているか
- 配置目的のcolumnや意味のないedgeがないか
- 再入力・再試行の戻り先があるか
- Technical mappingへ置くべき実装詳細をノード化していないか

## 現在の制約

- 構造はExperienceとRealizationの2層です
- RealizationからさらにSubflowを展開できません
- v2以前の仕様ファイルは読み込みません
