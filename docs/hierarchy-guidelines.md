# 階層構造の設計ガイド

## 目的

このドキュメントは、フローの全体像を保ちながら、実装・テストに必要な詳細へ分解するための判断基準を定めます。

階層化の目的は、単にノード数を減らすことではありません。レビューする人が必要な深さを選べるようにし、同じ仕様から次の2つを読み取れる状態を作ることです。

- 全体表示では、ユーザー価値とシステム間の因果関係を短時間で把握できる
- 詳細表示では、実装条件、入力検証、分岐、画面状態、テスト観点を確認できる

## 基本モデル

親ノードは「要約」ではなく、外側のフローに対する振る舞いの契約です。子フローは、その契約を満たすための検証可能な手順です。

~~~text
外側のフロー
  入力条件 ──> [ 親ノードが約束する振る舞い ] ──> 結果
                         │
                         └─ 子ノード + 子エッジ
                            入力・判断・画面状態・操作
~~~

親を閉じても外側の因果関係が成立し、親を開くとその内部で契約がどう実現されるかを説明できることが重要です。

## 混同しない3つの軸

表示レベル、構造の深さ、経路は別の概念です。

| 軸 | 答える問い | 例 |
|---|---|---|
| 表示レベル L1〜L3 | 同じノードをどの語彙で読むか | ログインを実行 / ログインボタンをクリックする / form.requestSubmit() |
| 構造の深さ | 1つの振る舞いを内部の手順まで開くか | ログインする → ID入力・検証・PW入力・検証・送信 |
| 経路 | どの結果の流れを見るか | 正常系 / 異常系 / すべて |

L3へ切り替えることは階層を深くすることではありません。ノード数とエッジ数は変えず、技術的な呼び方へ切り替えるだけです。

## 親ノードにする単位

親ノードは、次の条件を満たす単一の振る舞いとして定義します。

1. 1つの意図または結果を、主語と動詞を含む短い文で説明できる
2. 外側から見た開始条件と完了条件を定義できる
3. 内部の手順を隠しても、前後のノードとの因果関係を説明できる
4. ユーザーストーリーや受け入れ条件から参照する意味がある

よい親ノードの例:

- 認証情報を入力して送信する
- 配送先を選択する
- 注文金額を確定する
- 本人確認を完了する

避ける例:

- いろいろ入力する
- ログイン関連処理
- APIを3回呼ぶ
- LoginFormComponent

前者は振る舞いの契約を表します。後者は範囲が曖昧、または実装構造に依存しています。

## 子フローへ分解する基準

次のいずれかに当てはまる場合は、子フローへの分解を検討します。

- 独立して確認すべき入力項目や操作が複数ある
- 形式検証、権限判定、業務ルールなどの判断がある
- ボタン活性化、ローディング、エラー表示など、観測可能な画面状態が変わる
- 正常系と異常系で異なる手順や戻り先がある
- 再入力、再試行、キャンセルなどのループがある
- 1つの親ノードに複数の受け入れ条件やテストケースが対応する
- 実装担当者が、親ノードだけでは着手条件や完了条件を判断できない

目安として、独立した手順が3つ以上ある場合、または分岐・再試行が1つでもある場合は、分解する価値があります。

一方、次の内容は原則として子ノードにしません。

- ログ出力、メトリクス送信、単純な関数呼び出し
- フレームワーク内部のライフサイクル
- 振る舞いやテスト結果を変えない一時変数への代入
- 同じ意味の操作を実装都合だけで分割した処理

必要ならこれらは Technical mapping や関連リンクへ記載します。

## 階層の境界を決める基準

子ノードは親の契約の内側に留めます。次の境界を越える場合は、子ノードではなく外側の独立ノードにすることを優先します。

- ユーザーの目的が次の段階へ変わる
- ブラウザ、自システム、外部システム、永続リソースなどの責務境界を越える
- 後続処理から参照される業務上の事実や状態が確定する
- 別のユーザーストーリーから単独で参照する必要がある
- 失敗時の補償や運用判断を独立して扱う必要がある

ただし、責務境界を越えること自体が親の約束である場合は、複数トラックを持つ子フローとして表現しても構いません。その場合も、外側から見た親の開始条件と結果は1つに保ちます。

### ログイン例

今回のサンプルでは、親ノード「ログインする」の内部を次のように分解しています。

~~~text
会員ID入力
  → ID形式検証
  → パスワード入力
  → パスワード形式検証
  → ログインボタン活性化
  → ログインボタンクリック
~~~

IDやパスワードの形式エラーは、異常系の子ノードと再入力ループです。

ボタンクリック後の「ログイン要求」は自システムとの責務境界を越え、外側のフローから独立して参照されるため、親の内部には含めず、次のトップレベルノードとして扱います。

## 親と子の接続契約

親ノードの前後にあるエッジは、子フロー全体への入力と出力を表します。

- 親への入力エッジ: 子フローを開始できる前提
- 子フローの開始点: 正常系で外部からの入力を持たない最初の子ノード
- 子フローの終了点: 親の約束を満たし、外側の次ノードへ進める子ノード
- 異常系の終了点: 再入力、終了、または別の外側ノードへ接続する判断点
- 親からの出力エッジ: 子フロー完了後に外側へ渡す結果

子フローをレビューするときは、開始点から終了点まで途切れず到達できること、異常系が行き止まりになっていないことを確認します。

## トラックの使い方

トラックは子フロー内の責務や観点を分けるために使います。トップレベルのレーンより局所的な分類です。

ログイン例:

| track | 意味 |
|---|---|
| input | ユーザーが行う入力・操作 |
| rule | クライアント側の形式検証 |
| ui | ボタン活性化やエラー表示などの画面状態 |

トラックはノードの見た目を整えるためだけに増やしません。担当、テスト観点、責務のいずれも変わらない場合は同じトラックを使います。

## 粒度を揃えるルール

同じ子フロー内では、隣接ノードの粒度を揃えます。

- 「IDを入力する」と「入力イベントハンドラー内の正規表現を評価する」を並べない
- 操作、判断、状態、確定した事実を区別する
- 1ノードの Given / When / Then が1つの結果に収まるようにする
- ノード名は実装手段ではなく振る舞いを優先する
- 技術名は level3 と technical に分離する

1つの子ノードの説明に「〜して、〜して、〜する」が複数回現れる場合は、さらに分ける候補です。ただし、現在のビューは2階層までなので、分解後も複雑な場合は親の境界自体を見直します。

## ユーザーストーリーとの関係

ユーザーストーリーはトップレベルの親ノードを参照し、子ノードは親のスコープを継承します。

これにより、子ノードを追加・統合しても、ユーザーストーリー側の参照を大量に更新せずに済みます。特定の子手順だけが別のユーザーストーリーに属する場合は、親の境界が広すぎる可能性があります。

## 作成手順

1. まずトップレベルだけで、ユーザー価値が届くまでの因果関係を作る
2. 実装・テストに不足する親ノードを選ぶ
3. 親の開始条件、完了条件、外側へ渡す結果を一文ずつ定義する
4. 子ノードを操作、判断、状態、イベントに分ける
5. 正常系を開始点から終了点まで接続する
6. 異常系、再入力、再試行、キャンセルを追加する
7. トラックを割り当て、責務の混在を確認する
8. 全体表示へ戻し、親ノードだけでもフローが読めることを再確認する

## レビューチェックリスト

- 親ノードは1つの意図または結果として読めるか
- 親を閉じても前後の因果関係が成立するか
- 子ノードはすべて親の契約を満たすために必要か
- 正常系の開始点と終了点が明確か
- 異常系に戻り先または終了条件があるか
- L1〜L3の切り替えと階層の深さを混同していないか
- 技術詳細だけを理由に子ノードを増やしていないか
- 子ノードの追加で、別のユーザーストーリーまで親に混在していないか
- 全体、展開、フォーカスの各表示で読み取る対象が明確か

## 現在の制約

- 表示できる構造はトップレベルと子フローの2階層です
- 子ノードからさらにサブフローを展開する定義は検証エラーになります
- サブフローがないv2仕様でも、ルートに subflows: {} を明示します
- v1以前の仕様ファイルは読み込みません
